Reproducing DeepSeek-V3's FP8 Accumulation Problem Without a GPU

By Faizan A. Khattak · 24 November 2026

When DeepSeek trained DeepSeek-V3 in FP8 on NVIDIA H800 GPUs, they found that the tensor cores lose accuracy while summing the products of a matrix multiplication. Their fix was to move the partial sums out of the tensor cores at regular intervals and add them in FP32 on the ordinary CUDA cores.

In this article I reproduce that observation, and test the fix, using only bit-accurate software models of the tensor cores from the MATLAB Tensor Core toolbox. No GPU is needed. If you have not used the toolbox before, my previous post shows how to set it up.

1. What DeepSeek observed

In Section 3.3.2 of the DeepSeek-V3 Technical Report, the authors write that the accumulation precision of FP8 GEMM on H800 GPUs is “limited to retaining around 14 bits”. In a preliminary test with random matrices and an inner dimension of K = 4096, they measured a maximum relative error of nearly 2%.

To work around this, they let the tensor cores accumulate only NC = 128 elements at a time (four WGMMA instructions). The partial result is then copied to FP32 registers on the CUDA cores and added there. They call this promotion to CUDA cores.

Note: The H800 is a Hopper GPU, like the H100, and uses the same tensor-core arithmetic. Below I use the H100 model from the toolbox.

2. What the models tell us

A tensor core computes an inner product in blocks. For each block it multiplies NFMA pairs of inputs exactly, aligns the products to the largest exponent, keeps a fixed number of bits, adds them, and rounds the result. Two parameters describe how many bits survive the alignment step:

  • NFMA: how many products are summed in one block.
  • neab: how many extra alignment bits are kept beyond FP32's 23 fraction bits.

For FP8 inputs, the toolbox's H100 model uses NFMA = 32 and neab = −10. The aligned products therefore keep 2 integer bits and only 23 − 10 = 13 fraction bits. Every bit below that is truncated. The B200 (Blackwell) model uses neab = 2, so it keeps 25 fraction bits.

ModelFP8 block size NFMAFraction bits keptFP32 output
H100 (Hopper)3213truncated
B200 (Blackwell)3225truncated

A leading bit plus 13 fraction bits is 14 bits, which agrees with DeepSeek's description. The models were built from hardware measurements, independently of the DeepSeek report.

3. The experiment

I multiply two random matrices, A of size 64 × K and B of size K × 64, with inputs rounded to FP8-E4M3 and FP32 output. Each product is computed three ways:

  1. H100 tensor core, whole K: the entire inner product is accumulated inside the tensor core.
  2. B200 tensor core, whole K: the same, with Blackwell's wider alignment.
  3. H100 with FP32 promotion: the tensor core handles chunks of 128 along K, and the partial results are added in IEEE FP32 with round-to-nearest, mimicking DeepSeek's CUDA-core accumulation.

The reference is the exact product of the FP8 inputs, computed in double precision. The core of the script is short: 

inopts.format = 'fp8-e4m3';
A = cpfloat(randn(64, K), inopts);
B = cpfloat(randn(K, 64), inopts);
Dref = double(A) * double(B);              % reference

% 1) H100 and 2) B200, whole K inside the tensor core
D_h100 = H100TC(1, A, B, 0, 0, 'fp8-e4m3', 'binary32');
D_b200 = B200TC(1, A, B, 0, 0, 'fp8-e4m3', 'binary32');

% 3) H100 with promotion to FP32 every NC = 128 elements
NC = 128;
D_prom = zeros(64, 64, 'single');
for k0 = 1:NC:K
    idx = k0 : min(k0 + NC - 1, K);
    P = H100TC(1, A(:, idx), B(idx, :), 0, 0, 'fp8-e4m3', 'binary32');
    D_prom = D_prom + single(P);           % IEEE FP32 addition
end

err = @(D) norm(double(D) - Dref, 'fro') / norm(Dref, 'fro');

The full script, including the sweep over K used for the plot below, needs CPFloat and the toolbox's models/ and models/tools/ folders on the MATLAB path. It also runs in GNU Octave.

Show the full script (deepseek_fp8_accumulation.m) 
%% Reproducing the DeepSeek-V3 FP8 accumulation experiment with the
%  MATLAB Tensor Core models (H100 vs B200 vs "promoted" accumulation).
%
%  DeepSeek-V3 (arXiv:2412.19437, Sec. 3.3.2) reports that a GEMM of two
%  random matrices with K = 4096 on Hopper FP8 tensor cores gives a maximum
%  relative error of nearly 2%, and fixes it by moving partial sums to FP32
%  CUDA-core registers every N_C = 128 elements.
%
%  Requirements: CPFloat on the path, and models/ and models/tools/ of
%  https://github.com/north-numerical-computing/MATLAB-tensor-core
%  Works in MATLAB and GNU Octave.

clear; rng(1);

%% Parameters
M  = 64;          % rows of A      (keep small: the models are slow)
N  = 64;          % columns of B
K  = 4096;        % inner dimension, as in DeepSeek-V3
NC = 128;         % promotion interval used by DeepSeek-V3

inopts.format  = 'fp8-e4m3';
outfmt         = 'binary32';

%% Random inputs rounded to fp8-e4m3
A = cpfloat(randn(M, K), inopts);
B = cpfloat(randn(K, N), inopts);

% Reference: exact products of the fp8 inputs, summed in double precision
Cref = double(A) * double(B);

%% 1) H100 tensor core, whole K inside the tensor core
%     (fp8: blocks of 32, products aligned to 2 int + 13 frac bits, truncated)
D_h100 = H100TC(1, A, B, 0, 0, inopts.format, outfmt);

%% 2) B200 tensor core, whole K inside the tensor core (25 frac bits)
D_b200 = B200TC(1, A, B, 0, 0, inopts.format, outfmt);

%% 3) H100 with DeepSeek-style promotion: tensor core on chunks of NC,
%     partial results added in FP32 (round-to-nearest) on "CUDA cores"
D_prom = zeros(M, N, 'single');
for k0 = 1:NC:K
    idx  = k0 : min(k0 + NC - 1, K);
    P    = H100TC(1, A(:, idx), B(idx, :), 0, 0, inopts.format, outfmt);
    D_prom = D_prom + single(P);          % IEEE fp32 addition, RNE
end

%% Error measures
%  (a) element-wise relative error, (b) normwise relative error,
%  (c) error relative to |A||B| (the scale used in rounding-error bounds)
absAB = abs(double(A)) * abs(double(B));
err = @(D) struct( ...
    'max_elem_rel', max(abs(double(D(:)) - Cref(:)) ./ abs(Cref(:))), ...
    'norm_rel',     norm(double(D) - Cref, 'fro') / norm(Cref, 'fro'), ...
    'max_comp',     max(abs(double(D(:)) - Cref(:)) ./ absAB(:)));

E = {err(D_h100), err(D_b200), err(D_prom)};
names = {'H100 TC (full K)', 'B200 TC (full K)', 'H100 TC + FP32 promotion'};

fprintf('\nK = %d, M = N = %d, inputs fp8-e4m3, output fp32\n', K, M);
fprintf('%-28s %14s %14s %14s\n', 'Model', 'max elem rel', 'normwise rel', 'max |err|/|A||B|');
for i = 1:3
    fprintf('%-28s %14.3e %14.3e %14.3e\n', names{i}, ...
        E{i}.max_elem_rel, E{i}.norm_rel, E{i}.max_comp);
end

%% Optional: how the error grows with K (takes longer)
doSweep = false;
if doSweep
    Ks = 2.^(7:12);
    eH = zeros(size(Ks)); eB = eH; eP = eH;
    for j = 1:numel(Ks)
        Kj = Ks(j);
        Aj = cpfloat(randn(M, Kj), inopts);
        Bj = cpfloat(randn(Kj, N), inopts);
        Cj = double(Aj) * double(Bj);
        Dh = H100TC(1, Aj, Bj, 0, 0, inopts.format, outfmt);
        Db = B200TC(1, Aj, Bj, 0, 0, inopts.format, outfmt);
        Dp = zeros(M, N, 'single');
        for k0 = 1:NC:Kj
            idx = k0 : min(k0 + NC - 1, Kj);
            Dp  = Dp + single(H100TC(1, Aj(:,idx), Bj(idx,:), 0, 0, inopts.format, outfmt));
        end
        nrm = norm(Cj, 'fro');
        eH(j) = norm(double(Dh) - Cj, 'fro') / nrm;
        eB(j) = norm(double(Db) - Cj, 'fro') / nrm;
        eP(j) = norm(double(Dp) - Cj, 'fro') / nrm;
    end
    loglog(Ks, eH, 'o-', Ks, eB, 's-', Ks, eP, 'd-', 'LineWidth', 1.2);
    grid on; xlabel('K'); ylabel('normwise relative error');
    legend('H100 TC', 'B200 TC', 'H100 TC + FP32 promotion (N_C = 128)', ...
           'Location', 'northwest');
    title('FP8-e4m3 GEMM accumulation error');
end

4. Results at K = 4096

I measured the error in two ways. The normwise relative error compares the whole matrix with the reference. The componentwise error divides each entry's error by |A||B|, the scale that appears in rounding-error bounds for inner products.

Model ‖D − Dref‖F / ‖Dref‖F max |D − Dref| / (|A||B|)
H100 tensor core, whole K1.3 × 10−32.8 × 10−4
H100 with FP32 promotion (NC = 128)1.2 × 10−41.4 × 10−5
B200 tensor core, whole K5.7 × 10−81.9 × 10−8

With exactly the same inputs, the H100 result is about 20,000 times less accurate than the B200 result. The only difference between the two models is how many bits survive alignment. DeepSeek's promotion recovers about a factor of 10.

5. How the error grows with K

The plot shows three different behaviours.

  • H100 gets steadily worse. Its error grows by about a factor of 10 as K grows by a factor of 32. The tensor core truncates rather than rounds, so the error in every block points in the same direction and the errors pile up instead of cancelling.
  • Promotion makes the error independent of K. The FP32 promotion curve stays at the H100 value for K = 128. Each chunk of 128 has the same relative error, and the FP32 additions between chunks add almost nothing. This is why DeepSeek's fix keeps working for very long inner products.
  • Blackwell fixes the problem in hardware. With 25 fraction bits, the B200 model stays around FP32 accuracy. Its error also grows with K, for the same reason, but from a level about four orders of magnitude lower.

6. What about the “nearly 2%”?

My normwise error at K = 4096 is about 0.13%, well below 2%. The largest elementwise relative error in my run, by contrast, was over 100%. That number is dominated by entries of the product that happen to be close to zero, where dividing by a tiny exact value makes any error look huge.

The DeepSeek report does not say which error measure, matrix sizes or input scaling they used, so the exact 2% cannot be matched. What the models do reproduce is the qualitative picture: Hopper's FP8 accumulation is the bottleneck, the error grows with K, and promotion to FP32 caps it.

Research note: These results come from software models validated against the hardware, not from runs on an H100 or B200. The models match the hardware bit for bit on the inputs tested; see the papers below for the validation.

7. Why this matters

Accumulation precision is usually invisible to the people training models. It is not set by any software option, it is not documented, and it changes between GPU generations. The DeepSeek team found the problem the hard way, during large-scale training.

Bit-accurate models let you check a numerical concern like this in advance, on a laptop. You can compare GPU generations, test a workaround such as promotion to FP32, or choose a promotion interval before committing to a long training run.
